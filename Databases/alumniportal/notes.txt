    **GET /api/alumni/:id/full-profile — one query joining alumni row with (education + work_experiences + startups) tables for[Profile] using (LEFT JOIN, avoid row-count blowup issues)
        => Every profile required table has alumni_id as foreign key with alumni table id so we can use join (for alumni + ...)
        
        1. Raw Join Query (n*n):
            SELECT a.id AS alumni_id, a.name,
                e.school, e.degree,
                w.company, w.title,
                s.name AS startup_name
            FROM alumni a
            LEFT JOIN education e ON a.id = e.alumni_id
            LEFT JOIN work_experiences w ON a.id = w.alumni_id
            LEFT JOIN startups s ON a.id = s.founder_id
            WHERE a.id = 'al_riya';

        2. Aggregated JSON profile (production‑style): "to_jsonb()" it stores only 1 table info but we need 3 table for profiile:
            SELECT 
                a.id AS alumni_id,
                a.name,
                a.email,
                -- Aggregate education
                COALESCE(
                (SELECT json_agg(e) 
                FROM education e 
                WHERE e.alumni_id = a.id), '[]'
                ) AS education,
                -- Aggregate work experiences
                COALESCE(
                (SELECT json_agg(w) 
                FROM work_experiences w 
                WHERE w.alumni_id = a.id), '[]'
                ) AS work_experiences,
                -- Aggregate startups
                COALESCE(
                (SELECT json_agg(s) 
                FROM startups s 
                WHERE s.founder_id = a.id), '[]'
                ) AS startups
            FROM alumni a
            WHERE a.id = 'al_riya';

    OR 

        so EITHER we use: "jsonb_build_object()" with joins
                    SELECT 
                        a.*,
                        jsonb_build_object(
                            'education', COALESCE(json_agg(e) FILTER (WHERE e.id IS NOT NULL), '[]'),
                            'work_experiences', COALESCE(json_agg(w) FILTER (WHERE w.id IS NOT NULL), '[]'),
                            'startups', COALESCE(json_agg(s) FILTER (WHERE s.id IS NOT NULL), '[]')
                        ) AS profile
                    FROM alumni a
                    LEFT JOIN education e ON a.id = e.alumni_id
                    LEFT JOIN work_experiences w ON a.id = w.alumni_id
                    LEFT JOIN startups s ON a.id = s.founder_id
                    WHERE a.id = 'al_riya'
                    GROUP BY a.id;

                1. jsonb_build_object → builds a JSON object with named keys.
                2. json_agg(e) → aggregates all education rows into a JSON array.
                3. FILTER (WHERE e.id IS NOT NULL) → avoids nulls when no rows exist.
                4. GROUP BY a.id → ensures one row per alumni.

                    COALESCE(json_agg(e) FILTER (WHERE e.id IS NOT NULL), '[]')
                        * This version is used when you’re joining tables directly.
                        * Because of the join, you might get NULL rows if no education/work/startup exists.
                        * FILTER (WHERE e.id IS NOT NULL) ensures that only real rows are aggregated.
                        * COALESCE(..., '[]') guarantees that if no rows exist, you still get an empty JSON array ([]) instead of null.

                        👉 This is useful when you’re writing a GROUP BY query with joins.

            OR: This avoids the row multiplication trap entirely:

                    SELECT 
                        a.*,
                        jsonb_build_object(
                            'education', COALESCE((SELECT json_agg(e) FROM education e WHERE e.alumni_id = a.id), '[]'),
                            'work_experiences', COALESCE((SELECT json_agg(w) FROM work_experiences w WHERE w.alumni_id = a.id), '[]'),
                            'startups', COALESCE((SELECT json_agg(s) FROM startups s WHERE s.founder_id = a.id), '[]')
                        ) AS profile
                    FROM alumni a
                    WHERE a.id = 'al_riya';

                1. Each subquery independently aggregates rows into JSON. (no joins of tables level)
                2. No cross-product multiplication.
                3. Returns exactly one row per alumni with a nested JSON profile.

                    COALESCE((SELECT json_agg(e) FROM education e WHERE e.alumni_id = a.id), '[]')
                        * This version uses a correlated subquery.
                        * Each subquery runs independently for that alumni, so you don’t risk cross‑product multiplication.
                        * If the subquery finds no rows, json_agg returns NULL.
                        * Wrapping in COALESCE(..., '[]') again ensures you get [] instead of null.

                        👉 This is cleaner when you want one row per alumni with nested arrays, especially for API endpoints.

    **GET /api/events/low-turnout — events where ATTENDING count < 50% of total RSVPs (subquery/CTE + ratio)
      1.with rsvp_counts as ( --cte function
            select event_id,
                count(*) as total_rsvps,
                count(*) filter (where status='ATTENDING') as attending_rsvps
            from rsvps
            group by event_id	-- for each events table row need that's rsvp data categorized in 2 params 
        )

      2.select event_id from rsvp_counts where attending_rsvps > total_rsvps*0.5;

    *POST /api/events/:id/rsvp — upsert an RSVP (respect the alumni_id+event_id UNIQUE constraint — use ON CONFLICT)

        VALUES ('al_riya', 'ev_meet2026', 'ATTENDING')

        DO UPDATE SET status = EXCLUDED.status;


3. Jobs (GROUP BY, date filtering)
    GET /api/jobs?category=VACANCY&isActive=true
        select * from jobs where category='VACANCY' and is_active=true;

    *GET /api/jobs/by-company — GROUP BY company, COUNT(*) active postings
        select company, count(*) as active_postings
        from jobs where is_active=true group by company;

            👉 Rule of thumb:
                Use WHERE for row filters (like is_active = true).
                Use HAVING only for aggregate filters (like HAVING COUNT(*) > 10).

    GET /api/alumni/:id/jobs-posted — jobs posted by one alumnus

        SELECT *
        FROM jobs
        WHERE expire_at BETWEEN now() AND (now() + interval '7 days')
        ORDER BY expire_at ASC;

    **GET /api/normalization/variants?field=branch — DISTINCT raw branch strings not present in academic_options.value (anti-join / NOT IN / NOT EXISTS)
        {Using 3 anti‑join patterns}
        'Distinct' used for single row single entry showing even if same unnormalized word ex. 3row for 3 "CSE"

        1. Using "Not in":
            SELECT distinct a.branch from alumni a
            where a.branch not in (             #main diff.
                select ao.value
                from academic_options ao
                WHERE ao.type = 'BRANCH'
            );

        2. Using "Not exists":
            SELECT distinct a.branch from alumni a
            where not exists (                  #main diff. 1
                select 1                        #main diff. 2
                from academic_options ao
                WHERE ao.type = 'BRANCH'
                and ao.value=a.branch         #main diff. 3
            );
        
        2. Using "left Join with "is null" on right's table" for left-alumni(all branches data) right-academic_options(fixed corrected one's) : [so getting is null from right]
            SELECT distinct a.name, a.branch from alumni a
            left join academic_options ao
                on a.branch=ao.value ND ao.type = 'BRANCH'
                where ao.value is null; 

    **POST /api/normalization/merge — transaction: UPDATE alumni + UPDATE registration_requests + INSERT normalization_merge_logs, all-or-nothing
        "Normalization merge, as a transaction"- most imp. as we use 
            1. Begin -> 2. update alumni set branch="normalized_whatever"
            3. a matching UPDATE registration_requests -> 4. insert into "normalized_merge_logs" recording what changed
            5. commit

            -- Step 0: BEGIN;

            -- Step 1: Update alumni
            UPDATE alumni
            SET branch = 'Computer Science and Engineering'
            WHERE branch = 'CSE';

            -- Step 2: Update registration_requests
            UPDATE registration_requests
            SET branch = 'Computer Science and Engineering'
            WHERE branch = 'CSE';

            -- Step 3: Insert into normalization_merge_logs - [But this inserts id of all alumni's having matched branch not only justup to previous step1 alumni branch updations]
            INSERT INTO normalization_merge_logs (
                id,
                field,
                from_values,
                to_value,
                affected_ids,
                performed_by
            )
            VALUES (
                gen_random_uuid(),
                'branch',
                '["CSE"]',   -- JSON array of old variants
                'Computer Science and Engineering',
                (SELECT json_agg(id)::text FROM alumni WHERE branch = 'Computer Science and Engineering'),
                'system'
            );

            COMMIT;

        OR

        for properly getting mapped with only last step updated id's in upddate alumni/update registration_request - [so only those associated id got inserted in normalization_merge_logs]
            WITH updated_alumni AS (
                UPDATE alumni
                SET branch = 'Computer Science and Engineering'
                WHERE branch = 'CSE'
                RETURNING id
            ),
            updated_requests AS (
                UPDATE registration_requests
                SET branch = 'Computer Science and Engineering'
                WHERE branch = 'CSE'
                RETURNING id
            )
            INSERT INTO normalization_merge_logs (
                    id, field, from_values, to_value, affected_ids, performed_by
            )
            VALUES (
                gen_random_uuid(),
                'branch',
                '["CSE"]',
                'Computer Science and Engineering',
                (
                    SELECT json_agg(id)::text 
                    FROM (
                        SELECT id FROM updated_alumni
                        UNION ALL
                        SELECT id FROM updated_requests
                    ) t
                ),
                'system'
            );

    ***GET /api/alumni/suggested-connections/:id — alumni followed by people :id follows, excluding people :id already follows (2-hop graph query)
        with self‑join{following of :if following's}    skip id ke following ka self id ko follow Backend
                                                        skip id ke following ke following ko already follow(suggested ko already follow)
        
        SELECT DISTINCT f2.following_id AS suggested_id         --so actually returning following_id of 2nd nested query[followers of followers of id]
        FROM alumni_follows f1
        JOIN alumni_follows f2
        ON f1.following_id = f2.follower_id         -- “take those people al_riya follows (like al_karan), and see who they follow.”
        WHERE f1.follower_id = 'al_riya'            -- step 1: who al_riya follows
        AND f2.following_id <> 'al_riya'            -- exclude self
        AND f2.following_id NOT IN (                -- exclude already-followed:
            SELECT following_id                         --Don’t suggest people al_riya already follows directly.
            FROM alumni_follows
            WHERE follower_id = 'al_riya'
        );

        1. Using NULLIF:
            SELECT
                id,
                sent_count,
                total_targets,
                (sent_count::float / NULLIF(total_targets, 0)) * 100 AS percent_complete
            FROM notifications
            WHERE campaign_group_id = 'cg_123';

        2. Using CASE:
            SELECT
                id,
                sent_count,
                total_targets,
                CASE
                    WHEN total_targets IS NULL OR total_targets = 0 THEN NULL
                    ELSE (sent_count::float / total_targets) * 100
                END AS percent_complete
            FROM notifications
            WHERE campaign_group_id = 'cg_123';

    **GET /api/reports/alumni-by-batch-branch — "pivot"-style report: rows = batch_year, columns = branch, cell = COUNT(*) (CASE WHEN + GROUP BY, or crosstab)
        SELECT
            batch_year,
            COUNT(*) AS total,
            COUNT(CASE WHEN branch = 'Computer Science and Engineering' THEN 1 END) AS cse_count,
            COUNT(CASE WHEN branch = 'Computer Applications' THEN 1 END) AS bca_count
        FROM alumni
        GROUP BY batch_year
        ORDER BY batch_year;

            1. Each COUNT(CASE WHEN …) acts like a pivot column.
            2. Rows are grouped by batch_year.

    ***GET /api/reports/campus-engagement — per campus: alumni count, % registered, avg followers_count, event RSVP count (multiple JOINs + subqueries in SELECT list)
        1. Using Sub-Query:
            select c.id as campus_id,
            count(*) as alumni_count,
            avg(case when a.is_registered then 1 else 0 end)
            ::float * 100 as percent_registered,
            avg(a.followers_count) as avg_followers,
            (
                select count(*) from rsvps r
                where r.alumni_id in(
                    select id from alumni where campus_id=c.id
                )
            ) as total_event_rsvps
            from campuses c
            join alumni a
            on a.campus_id = c.id
            group by c.id
            order by c.id;

        2. Using Left JOin:
            SELECT
                c.id AS campus_id,
                COUNT(DISTINCT a.id) AS alumni_count,
                AVG(CASE WHEN a.is_registered THEN 1 ELSE 0 END)::float * 100 AS percent_registered,
                AVG(a.followers_count) AS avg_followers,
                COUNT(r.event_id) AS total_event_rsvps
            FROM campuses c
            JOIN alumni a ON a.campus_id = c.id
            LEFT JOIN rsvps r ON r.alumni_id = a.id
            GROUP BY c.id
            ORDER BY c.id;

        
    *****GET /api/reports/top-alumni-by-engagement — RANK() alumni by (followers_count + post count + connection count) using a window function
        with post_count as(
            select author_id, count(*) as post_count        --cte 1
                from posts
                group by author_id
            ),
            connection_count as(                            --cte 2
                select follower_id as alumni_id, count(*) as connection_count
                from alumni_follows
                group by follower_id
            )
            select
                a.id,
                a.name,
                a.followers_count,
                coalesce(p.post_count, 0) as post_count,
                coalesce(c.connection_count, 0) as connection_count,
                (a.followers_count + coalesce(p.post_count, 0), coalesce(c.connection_count, 0)) as engage_score,
                rank()over(order by(a.followers_count + COALESCE(p.post_count, 0) + COALESCE(c.connection_count, 0)) desc ) as rank
            from alumni a
            left join post_count p on a.id=p.author_id
            left join connection_count c on a.id=c.alumni_id
            order by rank;


        1. CTEs compute aggregates first.
        2. JOINs bring them into the main query.
        3. Window function RANK() assigns ranking by engagement score.
